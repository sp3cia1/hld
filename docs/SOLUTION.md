# Solution

## The approach

At startup the app reads the catalog into memory.

**Building a package:**

1. The builder tries every city plan: each order of distinct cities in the country, linked one to the next, at least 2 nights each, adding up to the trip.
2. For each plan it builds the cheapest valid package: flights, hotels with the fewest rooms that fit, transfers, and one attraction on each full day. Where parts depend on each other (flight, hotel and airport transfer), it searches the combinations rather than picking each part alone.
3. The cheapest total within budget wins. If none is within budget, the cheapest overall is shown, labelled as over budget.

**Checking it:** a validator, separate from the builder, checks every rule in §4 of the statement. It runs on every built package, after every change and before every export.

**Changing it:** every change follows one path. Apply it to a copy, repair what the app chose (how and when), validate, then save it or refuse with the reason ([0011](../../decisions/0011-repair-how-and-when-never-what.md)).

**Keeping it:** Postgres stores packages and confirmed reservations (a full snapshot), so both survive a page refresh and a backend restart.

## Scope and order

1. **Walking skeleton:** form → build one package → day-by-day plan → confirm → reopen by number. Tag `demo-1`.
2. **M6, minimum:** a change goes copy → repair step (empty for now) → validate → save, or refuse with the reason.
3. **The rest of the Musts:** M1 messages, M5 total, budget and export, M8 over budget.
4. **Good to have:** G1 (fill the repair step), G2 price differences, G4 three packages, G3 change cities.
5. **Proposed edges (confirm with Saumya):** "never a dead end" and "see what changed" (`IDEAS.md`).
6. **Then `IDEAS.md`,** by demo impact ÷ effort.

## Basics

Every team will have these, so we need them too (`docs/SLOP.md`):

- A rules panel on the package screen that shows the rules passing.
- A fuzz test: random requests through build, export and validate, checking that the total equals the sum of the parts.
- All rule numbers (60, 180, night limits) in one place, for the live code change.
- The restart moment in the demo: confirm, restart the backend, reopen the reservation.
- The frontend builds against a saved example package until the engine is ready.
- **Our own basic:** the overnight departure made obvious ("You leave Bengaluru on Fri 9 Apr at 23:50, the evening before your holiday starts"), with local times, the time zone, and "+1" where the date changes.
